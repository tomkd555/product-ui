# product-ui

One entry point for building and reworking web interfaces. Each screen is composed from what production screens of its kind carry (`references/real-screens.md`), every design decision lands in `tokens.json` (the colours, the type and the wording), and the result reaches the user once the check scripts and one independent reviewer have passed it. The lookup data and scripts under `scripts/lookup/` and `data/` come from ui-ux-pro-max, adapted to this skill (`THIRD_PARTY_NOTICES.md`). A citation of the form `research/<folder>` in this skill's files names the maintainer's research notes, which are kept outside the plugin.

`{SKILL_DIR}` is the absolute path of this skill's directory: `<plugin root>/skills/product-ui` under the plugin, `~/.claude/skills/product-ui` under a manual install. Under the plugin the agents carry the `product-ui:` prefix (`product-ui:review-design-lead`) and the hook registers itself; a manual install uses the bare agent names. The commands say `python`; on macOS and Linux run `python3`.

## Principles

1. **Real screens are the standard.** `references/real-screens.md` records what production screens of each kind carry: their regions, their sizes and their wording, measured on real screens (`research/20261106-real-screens/report.md`). A screen is composed from that record, and a check keeps a threshold only where real screens stay inside it.
2. **A screen ships inside its product.** Every real screen carries its product's header with the logo or the product name, its navigation where the kind has one (a sign-in or sign-up form carries the header alone), and the controls a screen of its kind has: a create action above a collection, a link from each row to its record, pagination. The build draws each one whose destination it holds. Every link and every control that opens a page leads to a view of this build; a view outside the build gets no link, button or navigation item, and an object without a view is named as plain text. The header shows the product name as text where `meta.logo` is `null`. On the `desktop` surface the window's title row stands in for the header, with the document's name and the product's name, and the window has no navigation of links and no footer (`references/desktop.md`). A control that changes the view of the data on its page (search, filter, sort, pagination, tabs) works on the sample data. A control never reports an effect it does not have, and a logo mark is drawn only from a file the user supplied.
3. **Tokens before markup.** The tokens are settled first and the implementation reads only those variables, because "did this file use a value outside the token set" is checkable. Wording follows the same rule: `tokens.json` carries a `voice` block, and `check_copy.py` asks whether the implementation used it.
4. **A string exists only if a product writer could defend it.** A label labels, an error says what to do, an empty state says the list is empty. Text that explains the screen, describes the layout, defends a number or fills a slot is deleted.
5. **Text is 14px or more.** Reading text is 16px, and the rows, cells and labels of a dense screen sit at 14px. A Latin-only run of at most 24 characters (a unit, a timestamp, a code) may go to 12px. A string that only fits at 11px is deleted. This minimum is this skill's own rule: real screens set metadata and dense rows smaller, and `references/real-screens.md` gives beside each real size the size to build with.
6. **Prohibitions live in scripts.** A rule written as "never do X" belongs in `check_slop.py`, `check_copy.py` or `check_shippable_text.py`, where a file can fail it.
7. **Review happens elsewhere.** Step 5 hands the rendered result to a reviewer who holds none of the context that produced it.
8. **The screen is composed before it is built.** `tokens.json` records who uses the product (`meta.users`), and `ui-brief.md` records, before any markup, the kind of screen and the regions it carries (`references/real-screens.md`), what the screen is for, who reads it, what dominates, in what order it is read and which container each section gets (`references/composition.md`). The reviewer judges the whole screen against that plan before judging its parts.
9. **Every visible choice has a source.** Colours, type and the logo record where they came from (`meta.provenance`, `meta.logo`), because a value equal to a known default with no recorded source shows that nobody chose it. The brief's `Brand area` line lists the brand elements the screen draws. Proof on a screen (figures, testimonials, customer logos) comes from the brief's Proof section or stays off the screen. Each collection, fetch and form has its empty, loading and error state in the brief.
10. **Each container carries what its pattern names.** What a row, a table, a card, a record's header or an empty state shows comes from a pattern in `patterns/`, drawn from what production design systems publish about that component and naming its sources (`references/patterns.md`). The brief ranks each object's properties by the reader's job, `scripts/patterns/resolve.py` picks the pattern and fills its slots from that ranking, and the same brief gives the same patterns and the same skeletons on every run.
11. **A screen is planned past its rest state.** Production screens differ from a mock in what happens after a click and in what the data does to the layout. The brief settles, before markup, which controls work and on what, the empty, no-results, error and validation state of each part, the step before each destructive action, and the sample records that test the layout: the longest name, the empty value, the extreme amount, every state of the object (`references/interaction.md`).
12. **Keys, words and messages follow the product family.** A screen proposed to people who work in a business package keeps that package's conventions: what Enter and each function key do, the word of each operation, whether a message asks before a registration, how a result is shown and for how long. `profiles/` records them per family of products, each value with the page it was read on (`references/profiles.md`). `tokens.json` names the profile, `resolve.py` writes its values into the brief's `## Conventions` section, and the skeletons and the kit carry them out, so the same brief gives the same keys and the same words on every run. The text minimum, the test of principle 4 and the button form hold under every profile.

## Out of scope

This skill covers interactive screens. These belong to other tools:

- HTML documents, reports, and a dashboard that is a static report page (a public status page is a screen of the Monitoring kind)
- Personas, journey maps, usability tests
- Logos, CIP, icon and social image generation
- PowerPoint decks

## Modes

| Mode | Condition | What runs | Cost |
|---|---|---|---|
| LIGHT | One local change to an existing screen, with tokens already in place | Steps 3 and 4 | scripts only |
| STANDARD | A new screen or page, or a redesign | Steps 0 through 6 | one review round |
| DEEP | A whole product surface, or the user asks for thoroughness | Steps 0 through 6, with every screen and state of the brief captured in Step 5 | one review round over all its screens |
| REMOVE | The screen exists and carries annotations or small text: 「注釈を消して」「サブテキストを削除して」「文字が小さい」 | The REMOVE procedure, then Step 4 | scripts plus the auditor |

One desktop window, with its file view, its panes and its save prompt as states, is one screen: the mode is STANDARD unless the request asks for several windows, which makes it DEEP. STANDARD escalates to DEEP once the surface spans more than one screen, and the escalation holds for the rest of the work. The steps of one flow on one route (入力, 確認, 完了) are one screen with states, and the brief lists each state. A state that only a server reaches in production (完了 after a submission, a sign-in error) is built and shown by a URL the brief names, such as `?state=done`, so the review can render it; the submit control moves to that URL, as the server's answer would, and the brief names the route a server would receive. A mock gives the same kind of URL to every other state the brief lists that a plain load of the entry does not show (確認, a validation error, an incident in progress on a status page). The single view behind a collection joins the build by the Structure answer of the intake. A view that stays outside (the create form behind 「新規」, the collection of another object, whether the request names that object or leaves it unnamed, the pages behind an account menu or a footer) gets no control on the screen: its navigation item, its button and its footer or menu entry are left off, a mention of its object is plain text, and the hand-over lists each control left off with the view it waits for. An address the product does not have shows the not-found screen inside the shell. The first line of the reply after intake states the mode and the reason, `Mode: STANDARD (one new screen, tokens.json absent)`, so the user sees the cost before any agent starts.

## Pipeline

When resuming interrupted work, decide the next step from which files exist, and from those alone: `tokens.json`, `theme.css`, `ui-brief.md` (with its `## Slots` table and, under a profile, its `## Conventions` table once `resolve.py` has run), `scaffold/`, the kit's parts under the project's source, the built output.

### Step 0: Intake

Skip this step when `tokens.json` exists and the request is a local change.

Detect the existing stack (`package.json`, `tailwind.config.*`, an `@import "tailwindcss"`); a project with none takes the defaults in `references/stack-defaults.md`. Then ask at most four questions in one AskUserQuestion round:

- **Surface**: landing page (`lp`, a marketing page), application (`saas`, a screen a person operates, behind a login or public: a search-results page, a sign-up form and a public-service form are applications) or desktop application (`desktop`, an application in its own window, built with Electron: `references/desktop.md`). A request for an Electron app, a desktop app, or an app that works like Word, Excel or PowerPoint settles `desktop` with no question.
- **Reference**: デジタル庁デザインシステム (`references/dads.md`) for public-sector sites, SmartHR (`references/smarthr.md`) for Japanese B2B SaaS dense with forms and tables, Astryx (`references/astryx.md`) for a `saas` application on Meta's design system, built with React 19 and Vite, or なし, where the tokens come from the request or from a product the user names. The same question settles the conventions, `meta.profile` (`references/profiles.md`, Choosing a profile): where the request asks for a screen of a Japanese core package (伝票入力, マスタメンテナンス, 「基幹システムの画面」) and names no product, its options lead with 国産の基幹パッケージ (`jp-core`), then the presets that fit and なし. A request that names a product or a platform of a family settles the profile and the product with no question, by the tables of `references/profiles.md`: 弥生販売 gives `jp-core` with `yayoi-hanbai`, 奉行Jシリーズ gives `jp-core` with `bugyo-j`, a product of that family without a table of its own (PCA, 奉行クラウド, OBIC7) gives `jp-core` with `meta.profile_product: null`, and freee会計, SmartHR, kintone, intra-mart, SAP, Salesforce and Dynamics 365 each give their own family. On `desktop`, the profile is `ms-office`, with `word`, `excel` or `powerpoint` where the request names the product the application should work like and `null` otherwise. A request that says its users are used to a named product records that group's `expertise` as `expert`, with the sentence as its `basis`. A profile settles the keys, the words and the messages; the look still comes from a preset, from the Brand answer or from the lookup.
- **Structure**: オブジェクト指向UI (OOUI) or タスク指向UI, recorded in `meta.structure` as `ooui` or `task`. Put first the one the table under "Choosing the structure" in `references/ooui.md` points to. A request that already names one settles it, and the question is left out. On `desktop` the question is left out and `meta.structure` stays unset: the window is the document window of `references/desktop.md`, which fixes its regions, so no structure is chosen, and `## Objects` and `## Slots` are written only for the panes' sections. Under `ooui`, a request that names an object's collection and leaves out the record its rows open gets one more question, whether the build holds that record view too; the default is yes, recorded in `meta.defaults_applied`, since a row that opens nothing is the first thing a reader of the screen tries. The action a screen exists for (問い合わせる on a listing, 申し込む on an event, 購入 on a product, 無料で始める on a landing page) is built with the screen: as a dialog on the page where the task is short (`references/interaction.md`, Editing), and as its form, added to the build by the same default, where the task needs a page. A landing page therefore comes with its sign-up form on a route of its own (the product name in the header, the fields, the submit and its result state), and the calls to action in the header, the hero and the closing band link to it.
- **Users**: the groups who use the product, each with a role, how often they use it (daily, weekly, occasional, first time), their expertise (novice, intermediate, expert) and the outcome they come for; a device or setting of use the request reports goes into the group's `context`. Offer the roles the request implies as options. The answer goes into `meta.users` with `basis: reported`; a group settled by default goes in with `basis: assumed`. An `lp` surface spends no question on it.
- **Brand**: the product's name, its colour, its typeface and its logo file. Asked only when the request names none of them. A preset named in the Reference answer overrides the colour and typeface of the Brand answer.
- **Stack**: a question only when the detection is ambiguous; otherwise the detected stack is recorded in `meta.defaults_applied`. `desktop` takes `electron-vite` with `vite-react`'s base (`references/stack-defaults.md`).

Take the questions in the order Surface, Reference, Structure, Users, Brand, Stack, and skip each one the request or the project already settles. A question the cap of four leaves out, or one the user cannot be asked, is settled by default and recorded in `meta.defaults_applied`: Surface from what the request builds; Reference as なし, or デジタル庁デザインシステム where the request builds a screen of a Japanese public body in a project that holds no component library yet; `meta.profile` as `null`, or the family the request names with its product (「担当者は弥生販売の操作に慣れています」 gives `jp-core` with `yayoi-hanbai`); Structure as the row of the table under "Choosing the structure" in `references/ooui.md` that the request fits (unset on `desktop`); Users with `basis: assumed` (a field the request states is `reported`, and `basis` may map each field to its own value; frequency defaults to `daily` for the staff of a work tool and `occasional` for the public, and expertise to `intermediate` at `daily` or `weekly` and `novice` at `occasional` or `first time`); Brand with colours from the lookup under `lookup:` provenance, `meta.logo: null` and the product name from the request, as the request writes it (「受注管理システム」 stays 「受注管理システム」). Where the request names no product, `meta.name` takes the request's own words for it (「アクセス解析」 from 「自社サイトのアクセス解析画面」), and `meta.defaults_applied` records the name as assumed. A screen of a public body names its operator in the header and the footer: where the request leaves the operator unnamed, the header shows the service's name, the operator is an open slot (`[TODO: 自治体名]`), and the hand-over asks for it. A Reference preset named in the request settles Brand with `reference:` provenance; when Reference is asked in the same round, Brand is asked too, and a preset answer overrides it.

Settle everything else by default and record each default in `meta.defaults_applied`; `register` defaults to 敬体 and `katakana_choon` to `jtf`. Read the interface language off the project's existing screens and copy, and spend no question on it; a new project, whose `lang="en"` is the scaffold's default, takes the language of the request, and the build sets `lang` to it. A frequency such as a few times a month is `occasional`.

### Step 1: Settle the tokens

Write `tokens.json` at the project root, in the shape `references/tokens-format.md` defines; `theme.css` and `ui-brief.md` sit beside it. `assets/tokens_example.json` is a filled-in example, and `assets/tokens_example.{dads,smarthr,astryx}.json` are the three presets.

- **Colours**: follow "Deriving the colours" in `references/tokens-format.md`. Route the arithmetic to `interfaces:better-colors` where it is installed, else follow those rules by hand and check each pair with `python {SKILL_DIR}/scripts/colour.py contrast "<a>" "<b>"`. Candidate palettes and pairings come from `scripts/lookup/search.py` (`references/lookup.md`) before a value is written by hand: `--design-system` with `--surface saas`, `--surface lp` or `--surface desktop`, and `--lang ja` on a Japanese interface. Beside a colour equal to a Tailwind default the lookup prints the value that clears T20; that value goes into `tokens.json`. The ground is light unless the request asks for a dark interface (`references/real-screens.md`, Every screen): the lookup prints its palettes for a light screen, with a white ground and the text at a lightness of 30% or under.
- **Fonts on `desktop`**: write `typography.display` and `typography.body` with `family` `Segoe UI Variable` and `family_ja` `Yu Gothic UI`, and the provenance `reference: references/desktop.md` for both, and run no font lookup: the lookup's faces come from Google Fonts, which a desktop window's content security policy blocks, and `references/desktop.md` (Look) fixes the face.
- **Voice**: write `terms` for the product, one word per operation, reading the words already on existing screens first. `assets/voice_terms.ja.json` carries the 長音 pairs C9 checks. Under a profile, `terms` also takes one entry for each operation whose profile word differs from this skill's own and does not contain it (`{"保存": "登録"}` under `jp-core`; under `ms-office` the save words 上書き保存 and 名前を付けて保存 contain 保存, so no term is written; `references/profiles.md`).
- **Profile**: write `meta.profile` and `meta.profile_product` as Step 0 settled them, `null` where the screens follow no product family. T24 refuses a name `profiles/` does not hold.
- **Reference**: when `meta.reference` names a preset, copy that reference's mapping. For any other reference product, work from a screenshot and a written description of it together.
- **Provenance**: write `meta.provenance` with one entry each for `color.primary`, `color.accent`, `typography.display` and `typography.body`, every value starting with `brand:`, `reference:`, `user:`, `lookup:` or `derived:` and naming the source. A palette taken from the lookup is recorded as `lookup:`; T20 warns on a Tailwind default colour from it: keep the colour with a ruling in the hand-over, or take the nearest darker lightness its message gives. Write `meta.logo` as the path of the product's logo file, or `null`; with `null` the header shows the product name as text, and no letter tile, monogram or drawn mark stands in for the logo. The favicon a starter ships (Vite's, Next.js's) is another product's mark: with `meta.logo: null` its `<link rel="icon">` is removed. On a `ja` interface, a type slot whose family is a Latin face takes a Japanese `family_ja` (T22).

### Step 2: Mechanical check on the tokens

```bash
python {SKILL_DIR}/scripts/validate_tokens.py tokens.json --json
python {SKILL_DIR}/scripts/generate_theme.py tokens.json
```

An error from `validate_tokens.py` sends this back to Step 1 before the generator runs. Rule on each warning in the hand-over: fix it, or keep it with a stated reason. `generate_theme.py` writes `theme.css` beside `tokens.json`: Tailwind v4 source, or plain CSS custom properties with `--plain` and for the `html` renderer. A project that already has a stylesheet joins it as "Using theme.css in an existing project" in `references/stack-defaults.md` says. Its `--text-*` scale starts at `text-xs` (12px, Latin-short only) and `text-sm` (14px); `text-base` and the steps above it are computed from `typography.scale` (`base_px` and `ratio`), and `--spacing` from `spacing.base_px`, so regenerating replaces Tailwind's fixed steps. Change `theme.css` only through `tokens.json` and the generator. When `meta.reference` is `astryx`, the "Project setup" in `references/astryx.md` runs once `theme.css` exists, before Step 3.

### Step 3: Build

Before any markup, read the section of `references/real-screens.md` for the kind of screen the request asks for. On `desktop`, read `references/desktop.md` first: the window is its shell, and the brief carries its `## Window`, `## Commands` and `## File view` sections; each pane's sections are composed from `references/real-screens.md`, `references/patterns.md` and `references/composition.md` like any screen's content, and the document area holds the application's own document, built as the application's component with no kind and no pattern (`references/desktop.md`, Document area). Then write `ui-brief.md` beside `tokens.json` from `assets/brief.template.md`: the screen's purpose in one sentence and the Composition section from `references/composition.md`, one block per screen (kind, regions, job class, reader, dominant element, reading order, density, archetype, grouping cue per section, what is constant and what is decided here, omissions, the tile row or `none`). The Regions line lists the regions the kind carries, the shell first; a region real screens usually carry is built unless the request rules it out or its content would be a fact about the business that the request does not give (steps 3 and 4 of "How to use it" in `references/real-screens.md`), and the Omitted line gives the reason for each one left out. When `meta.structure` is `ooui`, work through the three steps in `references/ooui.md` first and fill the brief's Structure section: the object table with each object's states, the actions each state allows and its relations, and the place each task of the request lands. The brief is the plan the Step 5 reviewer conforms the screen to, so a decision the markup departs from is changed in the brief first.

Then fill the brief's `## Objects` table and each block's `- Sections:` list (`references/patterns.md`; on `desktop`, for the panes' sections alone): one row per object, its properties ranked by the reader's job, and one line per section saying what it holds. The entry of a slip is one `slip` section, with the object of its lines and its totals; the maintenance of a master is one `master` section, with its groups; a list under search conditions adds `conditions` to its `records` section; a closing, an import and an approval are one `closing`, `import` or `approval` section each, the approval beside the sections that show the request. Run

```bash
python {SKILL_DIR}/scripts/patterns/resolve.py ui-brief.md
python {SKILL_DIR}/scripts/patterns/scaffold.py ui-brief.md
```

`resolve.py` picks each section's pattern from `patterns/index.json` and writes the `## Slots` table, then the `## Conventions` section, and on `desktop` the `## Command set` section (`references/desktop.md`): the keys, the words, the required mark, the confirmation and the messages of the profile `tokens.json` names, or `none` (`references/profiles.md`). When it stops, it names the one question the brief has to answer (whether the reader compares the records, which property is the identifier), and that question goes to the user when the request does not answer it. With the user out of reach, `compare` follows the kind's record in `references/real-screens.md`: `yes` for the records of a work tool, which its readers scan in columns, and `no` for a consumer result list of the row or tile variant; the brief records the choice as assumed. `scaffold.py` writes one skeleton per section under `scaffold/`, in the stack `tokens.json` names. The brief also carries the sections the checks and the reviewer read, with the template's structure and interaction questions kept as they stand for Step 5: `## Proof` (each figure, testimonial, customer logo and claim the screen shows, with its source; empty means the screen shows none), `## States` (per screen: each collection's empty state, each fetch's loading and error state, each form's validation), `## Sample data` (who supplied it; mock data varies names, dates and amounts and carries no statistic the reader did not ask for; what the product's own users write and rate, such as reviews, comments and a product's rating, is sample data, while what the operator claims about itself is proof) and, on `lp`, the lead content (what the reader sees first: the product itself, named). Sample data covers the content the product would hold (the names of people, sites and organisations, titles, message bodies, dates, amounts) and is invented for a mock, at the volume a production screen of the kind holds: a full page of records in a collection, the whole thread on a record. The interface's own strings follow the ban list. ### Step 5: Independent review

The step needs a renderable entry point, Node 22 or later, a Chrome install and the Agent tool. The entry point is served over HTTP: a bundler's `dist/index.html` loads its script as a module and renders blank from a `file://` URL. A build whose screens sit on path routes (`/orders/SO-1042`) is served by the bundler's preview command, which answers every route with the entry file (`npx vite preview --port <port> --host 127.0.0.1` in the project); a one-page or hash-routed build is served with `python -m http.server <port> --bind 127.0.0.1 --directory dist`. Render `http://127.0.0.1:<port>/`. On `desktop`, build the renderer (`npx electron-vite build`) and serve `out/renderer` the same way; the kit's host module stands in for the preload script in the browser, and the captures take the two sizes of `## Window` as `<width>x<height>` in place of 1280 and 375 (`references/desktop.md`, R52 to R55).

Complete the `ui-brief.md` written in Step 3: the built file paths, the entry file to render, the `Captures` list (each further screen of the brief and each state URL, as a name and a path) and whether the controls are wired. The Proof, States and Sample data sections stay; P3 compares the rendered screen with them. The template's Objects, Composition, Slots and Conventions sections, the eight cold-read questions, the seven copy questions, the three reader-fit questions, the seven interaction questions and the three content questions stay; the five conventions questions stay when `## Conventions` names a profile and are deleted otherwise; the Structure section stays when `meta.structure` is `ooui` and is deleted otherwise; the `## Window`, `## Commands`, `## File view` and `## Command set` sections and the five window questions stay on `desktop` and are deleted otherwise.

Then launch both agents in one message, `review-design-lead` with `model: sonnet` and `shippable-text-auditor` with `model: opus`. One `review-design-lead` reviews the whole brief: every further screen goes on its `Captures` list.

- `review-design-lead`, with `plan: ui-brief.md`, `target:` the directory the entry point is served from (the build output, `dist`, of a bundler project; else the project directory), and `scripts: {SKILL_DIR}/scripts/render`; it requires all three and returns `{"error": …}` when one is missing. It renders the entry and every capture the brief lists through headless Chrome at 1280px and 375px, or on `desktop` at the two window sizes of `## Window`, and measures each with `check_render.py` (R1–R55, with `--plan` reading the brief's job class for R15, its `## Conventions` section for R49 to R51 and its `## Window` and `## Command set` sections for R52 to R55). R7 measures the computed text size, which covers a size set from JavaScript or a transform; R12 to R15 measure nested enclosures, spacing steps, emphasis levels and equal tile rows; R16 to R20 flag gradient text, backdrop blur, one large radius on every container, a missing Japanese font and icon tiles above headings; R25 to R41 are the impeccable ports listed in the reference files; R42 to R48 measure whether each element that names its pattern carries its slots, and its status words (`references/patterns.md`); R49 to R51 compare what Enter, the function keys and the result message do with the brief's `## Conventions` section, on the captures taken with `PROBE` (`references/profiles.md`); R52 to R55 measure the window's scroll, its regions, its keys and its key tips (`references/desktop.md`). P2 answers the cold-read questions from the screenshot before reading the dump.
- `shippable-text-auditor`, with the built file paths and the `meta.surface` value (`saas`, `lp` or `desktop`) only; the brief and the reasoning stay with you. It returns `remove` and `rewrite` findings.

Rule on each finding individually: delete the string where the finding is that it should go, rewrite it where the finding is about wording, and keep it only under the carve-out in `references/ui-copy.md`, naming the clause in the hand-over.

The verdicts are 不合格 (BLOCK), 条件付き合格 (CONCERNS) and 合格 (CLEAN). 条件付き合格 and 合格 pass once every finding is ruled on. 不合格, or any critical finding, sends this back to Step 3. Two returns at most; report anything still unresolved as an open question.

When the step cannot run, write `Step 5 skipped: <reason>` in the hand-over. When the Agent tool is available, still launch `shippable-text-auditor` as above. The measured part needs no agent: serve the output, capture each width, and run both scripts over the dumps.

The key probe stops the submit and the clicks before the page's handlers, so no operation runs. A state that only an interaction reaches takes the script's third argument, a JavaScript expression run on the page before the dump, whose value the script prints to stdout: `node {SKILL_DIR}/scripts/render/cdp.js <url> 1280 "document.querySelector('form').requestSubmit()"`. The dump follows the expression at once, so an expression that starts a transition waits for it: `(async () => { document.querySelector('form').requestSubmit(); await new Promise(r => setTimeout(r, 400)) })()`. A React input takes its text through the native setter and an `input` event that bubbles: `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set.call(el, '冷蔵'); el.dispatchEvent(new Event('input', { bubbles: true }))`.

## REMOVE: stripping what already shipped

```bash
python {SKILL_DIR}/scripts/check_shippable_text.py <path> --json
```

Every finding is a deletion candidate here, warnings included.

1. Delete the whole element along with its string. A `<p class="hint">` emptied of its text still holds its margin.
2. Delete what the element leaves behind: the empty wrapper, the prop, the import, the class rule that has lost its last user.
3. Delete an annotation whole; a trimmed annotation is still an annotation. An ST7 run is raised to 14px or deleted, and the stylesheet rule that set it is fixed at its declaration (the finding names the selector).
4. Run `shippable-text-auditor` afterwards and delete what it returns. A `rewrite` verdict is deleted as well, unless the string names something the reader cannot get from the screen.
5. Keep a string only under an allowance named in `references/ban-list.md` (a constraint line under a field, a legend over an ambiguous encoding, a Latin-short run at 12px) and name the allowance in the hand-over.
6. Re-run the script until it reports only the strings kept that way, then run Step 4 in full.

## The hook

`hooks/ui_text_lint.py` is a PostToolUse hook in the plugin install; its reports carry the tag `[ui-text-lint]`. After every Write or Edit of a `.html`, `.htm`, `.css`, `.scss`, `.jsx`, `.tsx`, `.vue`, `.svelte` or `.astro` file, in any project, it runs `check_shippable_text.py --checks ST7,ST8,ST10` and reports the findings and the fix back to Claude. The write has already happened when it runs.

- **Error**: reported up to three times per file. Raise the size at the declaration it names, or delete the run, and write the file again.
- **Warning**: reported, and the write stands.
- **Skipped paths**: `node_modules`, `fixtures`, `vendor`, `dist`, `build`, `.git`, `*.min.*` and this plugin's own directory.
